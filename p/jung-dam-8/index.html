# 정담 개발 일지 #8 - 관리자 화면을 모바일 우선으로 갈아엎음

#7에서 보안 고치고 같은 날 밤에 이어서 한 작업이다.

관리자 페이지는 #3에서 만든 그대로였는데, 데스크탑 기준 좌우 2단 레이아웃이었다. 왼쪽에 메뉴 목록, 오른쪽에 편집 폼.

근데 사장님은 폰으로 쓴다. 2단이 폰에서 반씩 찌그러져서 둘 다 못 쓴다.

# 화면을 두 개로 쪼갬

900px 미만에선 한 번에 한 화면만 보여주기로 했다.

1

mobileView: 'list' | 'edit'

transform: translateX 로 슬라이드 전환한다. 목록에서 항목을 누르면 편집 화면이 옆에서 밀려 들어오고, 뒤로 가면 다시 나간다. 폰 앱에서 익숙한 그 동작이다.

상단 헤더도 화면마다 바뀐다.

화면 헤더
목록 메뉴 관리 + 로그아웃
편집 ← 목록 + 항목 제목 + 삭제

떠다니는 FAB 버튼은 통째로 없앴다. 편집 폼 위에 떠 있어서 입력칸을 가린다. “새 항목 추가"는 목록 화면 아래에 고정으로 뒀다.

데스크탑(≥900px)은 기존 2단 그대로 둔다. 둘 다 만족시키려다 둘 다 애매해지는 것보다 낫다.

# 언어 탭을 없앴음

이게 이번에 제일 크게 바꾼 것.

#6에서 관리자 화면에 언어 탭을 만들었다. 한국어 탭 / English 탭. 논리적으로는 깔끔한데 쓰기에 최악이었다.

  • 한국어 입력하고 탭 눌러서 영어 입력하고 다시 돌아와서 확인
  • 영어를 안 채웠는지 아닌지 탭을 눌러봐야 앎
  • 폰에선 탭 누르다가 키보드가 올라왔다 내려갔다 한다

그래서 탭을 없애고 둘 다 항상 보이게 했다.

1
2
3
4

1. 이미지     — 전체 폭, 누르면 업로드
2. 가격       — $ 접두사 고정
3. 한국어  — 제목 / 재료 설명    (배경색 있는 카드)
4. English — Title / Ingredients (배경색 있는 카드)

영어를 보려면 스크롤을 내려야 하지만, 번역이 비었는지가 스크롤 한 번으로 보다. 탭으로 감춰두는 것보다 이게 훨씬 나았다.

가격 입력칸엔 $ 를 고정으로 박아뒀다. 매번 타이핑하던 걸 없앤 것.

# 저장 버튼을 하나로 줄임

#3에서 POST(전체 저장)랑 PATCH(항목 저장)를 둘 다 만들었다. 그래서 화면에 버튼이 두 개 있었다.

1
2

[모든 변경사항 저장]   ← POST
[저장]                ← PATCH (항목 하나)

사장님 입장에서 이건 그냥 “뭘 눌러야 되는지 모르겠는 버튼 두 개” 이다. 둘 다 눌러야 하나? 하나만 누르면 날아가나?

“모든 변경사항 저장"을 없앴다. 항목 단위 저장 만 남긴다. POST API는 그대로 두되 화면에서 뺐다. 새 항목을 추가할 땐 지금 보고 있는 카테고리가 자동으로 선택되게 한다.

모바일에선 저장 버튼을 편집 화면 하단에 고정으로 붙였다. 긴 폼을 끝까지 스크롤해야 저장할 수 있던 걸 없앤 것.

# 토스트를 아래로 내림

알림 메시지가 화면 상단에 떴는데, 폰에서 상단은 엄지가 제일 안 닿는 자리이다. 하단 중앙으로 옮겼다.

# 목록에 썸네일

목록에 제목만 있으니까 어떤 메뉴인지 바로 안 보였다. 이미지가 있는 항목은 작은 썸네일을 같이 띄우게 한다. 메뉴판은 결국 사진으로 기억하는 거라서 이게 체감이 컸다.

# 이번엔 설계 문서부터

#5에서 재미를 봐서 이번에도 문서를 먼저 썼다.

1
2

docs/superpowers/specs/2026-03-25-admin-mobile-ux-design.md
docs/superpowers/plans/2026-03-25-admin-mobile-ux.md

스펙에 Status: Approved 라고 적어놓고 시작한다. 혼자 하는 프로젝트에 승인이 무슨 의미인가 싶은데, “여기까지 정했으니 이제 코드 치는 동안은 다시 고민 안 한다” 는 선 긋기로는 쓸모 있었다.

바뀐 파일은 두 개뿐이다.

1
2

src/app/admin/page.js          — 상태, 레이아웃, 폼 구조
src/app/admin/page.module.css  — 슬라이드 전환, 카드, $ 접두사, 토스트 위치

# 느낀 점

언어 탭이 제일 큰 교훈이었다. 데이터 구조가 { ko, en } 이니까 UI도 탭으로 나누는 게 자연스러워 보였는데, 쓰는 사람한텐 “한 메뉴를 등록한다"는 하나의 작업이다. 구조를 그대로 화면에 옮기면 안 되는 거였다.

저장 버튼 두 개도 같은 실수다. API가 둘이니까 버튼도 둘로 만든 것. API 모양이랑 화면 모양은 따로 결정해야 한다.

#6에서 붙인 Analytics로 방문자 대부분이 모바일인 걸 봤는데, 정작 관리자 화면은 데스크탑 기준이었다. 손님 화면만 모바일을 챙기고 있었던 셈이다.
