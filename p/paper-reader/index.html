# 논문 읽기 (번외) - 읽는 도구를 직접 만들었음

#1에서 “논문 열기 전에 질문 받고 내 답부터 적는다"고 썼는데, 그 방식을 손으로 지키기가 어렵다.

매번 같은 순서로 질문 받아야 하고, 답을 같은 형식으로 남겨야 하고, 프로필이랑 열린 질문을 그때그때 갱신해야 한다. 한두 편은 되는데 열 편째에는 무너진다.

그래서 Claude Code 플러그인으로 만들었다. 이름은 paper-reader.

커밋 날짜 보면 이런다.

9/2에 만들고 9/3에 한 번 크게 고친다. 고친 이유가 이 글의 절반이다.

# 요약해주는 도구가 아님

README 첫 문단에 이렇게 박아뒀다.

논문을 대신 요약해 주는 도구가 아니다. 읽는 동안 질문을 던져 사용자가 스스로 생각하게 만들고, 그 생각을 남기는 것이 목적이다.

요약은 이미 차고 넘친다. 초록도 요약이고, 블로그 정리 글도 요약이고, 모델한테 던지면 3초 만에 나온다.

근데 #2에서 제일 값졌던 건 요약이 아니라 내가 d_k를 ‘보는 토큰 수’로 잘못 알고 있었다는 사실이었다. 요약만 읽었으면 영원히 몰랐을 듯.

그래서 도구 목표를 “좋은 요약 생성"이 아니라 “내 오답을 끌어내서 기록” 으로 잡는다.

# 커맨드 6개

커맨드 하는 일
/paper-init 저장소 초기화 + 프로필 첫 재료를 질문으로 받음
/paper-read <id|PDF> 두 패스로 정독
/paper-next 내 관심사·열린 질문·별점 근거로 다음 논문 추천
/paper-trend <주제> 최근 흐름 묶어서 trends/ 에 저장
/paper-recall <검색어> 읽은 논문이랑 그때 내가 한 말을 되찾음
/paper-profile 관심사·배경·입장·열린 질문 확인 및 갱신

커맨드 없이 “이 논문 읽자"고 해도 스킬이 알아서 붙는다. 커맨드는 명시적 진입점일 뿐이다.

# 9/3에 고친 것 — 정독을 두 패스로 쪼갬

처음 버전은 섹션 설명하면서 중간중간 질문을 끼워 넣었다. 돌려보니 둘 다 얕아졌다. 설명이 질문 때문에 끊기고, 질문은 설명 흐름에 눌려서 형식적으로 답하게 된다.

그래서 논문 위를 두 번 지나가게 바꾼다.

2
3

예측      제목·초록만 보여주고 "당신이라면 어떻게 풀겠어요?"   질문 1개
  ↓
1차 통독   스토리라인·기여 → 섹션별 요약                      질문 없음
  ↓       "여기까지 이해되셨나요?"
2차 검증   5단계로 되짚으며 질문                              단계당 1개

예측 질문이 맨 앞에 있는 이유는 답을 보기 전에 물어야 값이 있어서다. 답 받아두고 통독한 뒤, 2차 1단계에서 논문 답이랑 대조.

#3의 “흥미로운데, 만약 헤드를 때도 성능이 안떨어진다는 가정하에면…“이 바로 그 예측 질문의 답이다. 논문 읽고 나서였으면 절대 저렇게 답 안 했을 것.

그리고 2차 질문은 논문 길이랑 무관하게 다섯 개로 고정한다. 섹션이 여덟 개인 논문이라도 다섯 개. 5단계가 질문 개수를 묶어주는 장치 역할을 함. 없으면 섹션 수만큼 질문이 늘어나서 끝까지 못 간다.

# 설계 결정 3가지

# 1. 프로필은 append-only

입장이 바뀌어도 이전 문장 안 지우고 날짜랑 계기 붙여서 덧붙인다.

요약본은 다시 만들 수 있지만 생각이 바뀐 궤적은 한 번 지우면 복구되지 않는다.

실제로 이게 값을 했다. #3에서 “깊이는 골고루 분포"라고 했다가 “아니, 실험이 약한 것"으로 옮겨간 게 stances.md 에 두 줄로 남아 있다. 최종 결론만 적었으면 안 남았을 것.

# 2. 판단은 모델이, 정합성은 스크립트가

요약·질문·추천처럼 규칙으로 못 적는 일은 프롬프트에 남기고, 인덱스 누락·중복 노트·깨진 링크처럼 조용히 어긋나는 일은 파이썬 스크립트가 막는다.

이 도구의 실패 모드는 요약이 부실한 게 아니라 아카이브가 어긋나는 것이다.

요약이 좀 부실하면 다시 읽으면 된다. 근데 노트가 중복 생성되거나 인덱스가 실제 파일이랑 어긋나기 시작하면, 그건 한참 뒤에야 알아차리고 그때는 이미 손으로 못 고칠 만큼 쌓여 있다.

# 3. index.md 를 안 읽음

아카이브 훑을 때 인덱스를 통째로 읽지 않고 notes.py list --status done --tag rag 처럼 필터를 건다. 논문이 수백 편이 돼도 토큰 비용이 평평한다.

# 저장소 구조

플러그인(로직)이랑 노트(데이터)는 분리된다. 노트 저장소는 내 git 저장소고, 플러그인은 따로 업데이트된다.

~/papers/
  index.md             # 스크립트가 재생성 — 손대지 않음
  reading-list.md      # 읽을 후보 큐
  notes/<arxiv-id>.md  # 논문 한 편 = 파일 한 장
  profile/
    interests.md       # 관심사      → 추천의 주 입력
    background.md      # 지식 수준    → 설명 깊이 조절
    stances.md         # 의견·관점
    questions.md       # 열린 질문    → 추천의 두 번째 축
  trends/YYYY-MM.md

background.md 가 실제로 설명 깊이를 바꾼다. 내 프로필엔 “딥러닝 기초는 익숙한다 / 논문 수식은 따라감 / 강화학습은 약함"이 적혀 있어서, 어텐션 수식은 유도만 던지고 넘어가는데 PPO 쪽은 비유부터 시작하게 된다.

# PDF 읽기 — poppler 있으면 그림을 봄

arXiv HTML 없는 논문이랑 손에 든 PDF를 위해 경로가 두 개다.

  • poppler 있음: PDF 페이지를 이미지로 렌더링해서 그림·표·수식을 실제로 보고 해설한다. #3에서 “Figure 6의 y축이 90%에서 시작하는 절단 축이고 오차 막대가 없다"를 잡아낸 게 이 경로 덕분이다. 텍스트만 뽑았으면 못 봤다.
  • 없음: 순수 파이썬 텍스트 추출로 폴백. 그림이랑 표가 빠지고 수식이 깨진다. 추출 품질을 스스로 채점해서 낮으면 그 사실을 알리고 poppler 설치를 권한다.

로컬 PDF는 첫 장에서 제목 뽑아서 arXiv에 같은 논문 있는지 먼저 확인한다. 있으면 arXiv id를 씀. 같은 논문을 PDF로 다시 읽어도 노트가 갈라지지 않게 하려고.

# 느낀 점

도구 만들고 나서 논문 두 편 읽었는데, 제일 크게 바뀐 건 속도가 아니라 내가 틀린 걸 남기게 됐다는 점이다. 예전엔 읽다가 “아 그게 아니구나” 하고 넘어갔는데, 이제는 그 “아 그게 아니구나"가 파일에 남는다.

9/3에 정독을 두 패스로 쪼갠 것도 결국 같은 얘기다. 설명이랑 질문을 섞으면 둘 다 얕아진다는 건 도구를 써보기 전엔 몰랐다.

도구 만들고 → 써보고 → 도구 고치는 순환이 한 바퀴 돌아간 셈인데, 한 바퀴에 논문 한 편이면 나쁘지 않은 듯.
